# Format and design notes

Everything here is an implementation decision with a reason attached, so that
the next person can change a number knowing what it was holding up.

## Table layout

All six double-byte code pages share one flat indexing scheme:

```
index = (lead - 0x81) * 191 + (trail - 0x40)
```

`191 = 0xFE - 0x40 + 1`, so the table covers lead bytes `0x81..0xFE` and trail
bytes `0x40..0xFE` — 24 066 slots per code page, of which most are zero.
A zero means "this pair is not mapped", which is unambiguous because U+0000 is
never a two-byte code-page character.

Sharing the layout across code pages means one lookup function, one reverse-
index builder, and one set of bounds checks instead of six. The cost is that
sparse pages (EUC-KR maps only `0xA1..0xFE` × `0xA1..0xFE`) waste slots: EUC-KR
uses 8 225 of 24 066.

Why not a hash map or a sorted array of pairs? Because a table index is a single
multiply and add, the whole thing is `const`-ish data the compiler can place in
a data segment, and no allocation happens per character. Detection decodes the
same bytes thirteen times, so per-character cost matters.

Shift_JIS half-width katakana (`0xA1..0xDF`, single bytes) are computed —
`U+FF61 + (byte - 0xA1)` — rather than tabulated. They are a linear range; a
table would be 63 redundant entries and one more thing to get wrong. EUC-JP
spells the same block as `0x8E` followed by `0xA1..0xDF`, so the same
arithmetic applies one byte later.

### EUC-JP is two tables, not one

EUC-JP has three forms, and only one of them fits a two-byte slot:

| Form | Bytes | Repertoire | Stored as |
|---|---|---|---|
| ASCII | `0x00..0x7F` | ASCII | passthrough |
| half-width katakana | `0x8E` + `0xA1..0xDF` | U+FF61..U+FF9F | computed |
| JIS X 0208 | `0xA1..0xFE` × `0xA1..0xFE` | 6 879 characters | the shared pair table |
| JIS X 0212 | `0x8F` + `0xA1..0xFE` × `0xA1..0xFE` | 6 067 characters | its own 94×94 table |

JIS X 0212 is the supplementary kanji set that only ever appears behind the
`0x8F` prefix, so it gets a second table indexed by cell coordinates rather than
by lead/trail. Folding it into the pair table is not possible without losing
either the prefix or the pair, and the two-level split mirrors the standard.

Encoding goes the other way round: the pair table is consulted first, and only
characters with no JIS X 0208 spelling fall through to the 0212 table. A
character mapped in both levels therefore keeps its standard, two-byte form, and
a round trip is stable.

### GB18030 is two mechanisms, not one

GB18030 keeps GBK's two-byte table and adds two things on top: 2 149 private-use
slots, and a four-byte form that reaches every code point in Unicode.

The four-byte form is spelled `lead digit lead digit`, where a digit is
`0x30..0x39`. That is also what tells it apart from the two-byte form: a
two-byte trail never goes below `0x40`, so the two shapes cannot collide, and no
lookahead beyond the second byte is needed to know which one is being read.

The four bytes are not a character code — they are a *pointer* into a mixed-
radix space:

```
pointer = (b1 - 0x81) * 12600 + (b2 - 0x30) * 1260 + (b3 - 0x81) * 10 + (b4 - 0x30)
```

Below 189 000 the pointer selects a code point in the BMP through a run table:
pointer 0 is U+0080, and the mapping advances one code point per pointer,
skipping every character that already has a two-byte spelling. Those skips are
the only reason a table is needed at all — without them the BMP would be
`0x80 + pointer`. The table has 206 runs, generated by decoding, not typed.

From 189 000 upwards the standard *is* arithmetic: `pointer - 189000 + 0x10000`,
which is U+10000..U+10FFFF. Pointers between the end of the BMP run table
(39 420) and 189 000 are holes, and decode to U+FFFD.

Encoding tries the two-byte table first and falls back to the four-byte form,
which is why a character mapped both ways keeps its two-byte spelling and a
round trip is stable. Because every scalar value has a four-byte spelling,
`--to gb18030` cannot fail.

### Why GBK is reported for a file that reads as both

GB18030's byte language is a superset of GBK's: same two-byte table, plus more.
So every GBK file also decodes cleanly as GB18030, to the same text. Left alone,
detection would report every Chinese file as `ambiguous — gbk and gb18030`,
which is true and useless.

`Charset::narrows` names the one strict subset relation among the supported
pages, and `detect` drops a candidate when another candidate decodes the same
bytes to byte-identical text and is narrower. This is not a guess about which
name the user wanted: the bytes contain no evidence of using GB18030's extra
room, so the label that claims less is the one supported by evidence. A file
that does contain a four-byte sequence cannot be read by GBK at all — GBK counts
an error there — so the wider page wins on its own merits.

## Generation

`scripts/gen_tables.py` reads CPython's own codecs and writes
`src/mojibake/tables_gen.mbt`. Nothing is copied from a third-party library, and
the script is committed so the tables can be regenerated and diffed. The header
of the generated file says so.

Byte pairs that CPython rejects are left as 0. This is a deliberate choice to
track CPython exactly, and it means one real-world quirk is *not* modelled:
Microsoft's CP936 maps the single byte `0x80` to `€`, while Python's `gbk` codec
rejects it. MoonMojibake follows Python. If a file relies on the Microsoft
behaviour, that byte is reported as an error and counted.

## Common-character set

The frequency signal needs a notion of "characters people actually write". The
obvious approach — ship a frequency corpus — costs hundreds of kilobytes and
raises a licensing question.

Instead the generator derives the set from the standards themselves:

- GB2312 level 1, lead `0xB0..0xD7`, trail `0xA1..0xFE` — 3 755 frequent
  **simplified** characters, ordered by pinyin precisely because they are the
  common ones.
- Big5 level 1, lead `0xA4..0xC6` — 5 495 frequent **traditional** characters,
  same reasoning.

The union is 9 156 characters. Membership is a free, defensible, script-neutral
"is this in common use" test, and it is symmetric across simplified and
traditional, which matters: if only GB2312 level 1 were used, every traditional
character would look rare and Big5 would lose to GBK on its own text.

Measured on the test corpus, real Chinese hits this set at ~100% and a wrong
code page's output at ~0%. That gap is what the 35-point frequency signal
exploits.

## Scoring

`text_score(text, errors) -> Int` in `0..100`. Five weighted signals:

| Signal | Max | Computation |
|---|---|---|
| Clean decode | 30 | 30 if no errors; otherwise `30 - 30*errors/chars - 8`, floored at 0 |
| Script coherence | 15 | `15 * (dominant_script + neutral) / chars` |
| Character frequency | 35 | scaled by the CJK share, see below |
| Printability | 10 | `10 * (chars - noise) / chars` |
| Script exclusivity | 10 | 10 when ≥90% Hangul or ≥40% full-width kana, and no errors |

Then a penalty: `-12` when Hangul is mixed with ideographs or kana beyond a
third of the scripted characters.

### Why the error penalty is not proportional

`30 - 30*errors/chars` alone is too weak. One bad sequence in a 32-character
stream costs one point, which is less than the frequency bonus GBK earns from
almost-parsing Western text. The extra flat `-8` encodes the actual prior: a
code page that cannot consume the whole stream is the wrong code page, and one
failure is already strong evidence.

### Why a private-use character counts as a near miss

GB18030 has 2 149 two-byte slots that map into U+E000..U+F8FF, the private-use
area. Those slots exist so that legacy GB2312 private-use bytes round-trip; they
do not spell characters anyone writes, and no font can be expected to show them.

Before this was modelled, a windows-1252 sentence decoded as GB18030 came out at
score 53 against 52 for the correct reading: the private-use slot let GB18030
consume a byte pair GBK rejects, which bought the full "clean decode" 30 and
outweighed the evidence for the real code page. Counting each private-use
character as an error brings that reading back to 44, where it belongs.

The rule stated generally: a decode is only clean if every character it produced
is one the page *assigns* a meaning to. A slot that exists for round-tripping is
not an assignment.

### Why frequency scales with the CJK share

Without the `* scripted / chars` factor, a Western sentence containing two
accented characters that Shift_JIS reads as two common kanji would earn the full
35 points for those two characters — as much as a page of Chinese. Scaling by
the share means the frequency evidence only counts for the part of the text it
explains. This single line is what stopped Latin-1 text from being detected as
Shift_JIS.

### Why half-width katakana is not "neutral"

`is_neutral_char` counts ASCII, CJK punctuation and fullwidth forms as belonging
to whatever script dominates. Half-width katakana (`U+FF61..U+FF9F`) lives in
the same fullwidth block and had to be excluded explicitly, because a Chinese
code page read as Shift_JIS produces exactly that and nothing else. Counting it
as neutral made that accident look like ordinary punctuation.

### Telling Japanese from Chinese

EUC-JP and Shift_JIS both nest inside GBK: every byte they can use is also a
valid GBK byte, so a Japanese file always decodes as Chinese with zero errors.
Worse, GBK reserves rows `0xA4`/`0xA5` for the same kana block, so the Chinese
reading keeps the kana too — "の" and "カタカナ" survive byte-for-byte. The kana
count therefore cannot decide, which is why adding EUC-JP first produced a
55-byte Japanese sample that tied at 88/88 and lost the tie on candidate order.

What does decide is the kanji. The first test tried was "is this kanji in the
JIS repertoire at all", and it failed: JIS holds about 7 000 ideographs and
therefore most Chinese hanzi as well, so `泣塑胳矢鞠戳机` passed as readily as
`日本語文章漢字`. JIS X 0208 **level 1** is a frequency set — 2 965 kanji that
newspapers are expected to stick to — and the Chinese reading fails it often
enough to be visible.

The penalty is measured against the ideographs, not the whole text, because
kana and punctuation carry no evidence either way:

```
penalty = 30 * (kanji outside JIS level 1) / (all kanji)     # only when kana > 0
```

A Chinese reading of Japanese bytes loses 10–20 points; an honest Japanese
reading loses nothing, since by construction all of its kanji came from the
standard. Text with no kana is untouched, so GBK, Big5 and EUC-KR detection
keep the behaviour they had before EUC-JP existed.

## Detection

Candidates come from `Charset::all()`, in this order:

```
utf-8, gbk, gb18030, big5, shift_jis, euc-kr, euc-jp, windows-1252, latin1,
utf-16le, utf-16be, utf-32le, utf-32be
```

Sorting is a stable insertion sort, so ties resolve to this order. That is why plain ASCII comes back as UTF-8 rather than as whichever code
page was tried last.

`confidence = clamp((top - second) * 3, 0, 100)`, scaled down when the top score
is below 40, and floored at 85 when the winner's text satisfies the script-
exclusivity test with zero errors. A confidence of 0 means "the candidates are
indistinguishable", which is the honest answer for ASCII.

### The UTF-8 rule

If the bytes decode as UTF-8 with zero errors **and** contain a byte ≥ `0xC2`,
the UTF-8 candidate is forced to 100.

This is not a heuristic in the same family as the others; it is close to proof.
A legacy code page that happens to form valid multi-byte UTF-8 across an entire
file is astronomically unlikely, while UTF-8 read as a legacy code page is
routine. The rule is also what makes mojibake files work: a mojibake file *is*
valid UTF-8, of garbage, and without this rule the detector would attribute it
to GBK and hide the problem.

The `≥ 0xC2` condition keeps pure ASCII out of it — ASCII is valid UTF-8 but
proves nothing, and forcing it to 100 would fabricate confidence.

### The UTF-16 rule

BOM-less UTF-16 is halved unless it shows the alternating-zero pattern: at least
half of its code units have a zero high byte.

Without this rule UTF-16 wins everything. Any even-length byte stream decodes
into something, and arbitrary pairs land in Hangul (EUC-KR/GBK byte pairs are
in the `0xB0..0xFE` range, which is exactly the Hangul block), where they score
90+ because Hangul is a plausible script and we have no Korean frequency model.

The cost is that a genuine BOM-less UTF-16 file holding CJK text is discounted
too. That is the right trade: UTF-16 without a BOM is rare, UTF-16 with a BOM is
detected exactly, and a false positive here poisons every other result.

### The UTF-32 rule

UTF-32 gets the same treatment as UTF-16, with one extra requirement: at least
half of its code units must have an all-zero high half. For Latin text that
number is 100%; for CJK it is still most of them, since every code point up to
U+FFFF has two zero bytes above it.

The ordering in `bom_charset` is load-bearing. A little-endian UTF-32 BOM is
`FF FE 00 00`, which *starts with* the UTF-16LE BOM `FF FE`. Checking the
two-byte BOM first would classify every UTF-32LE file as UTF-16LE and leave a
`NUL` glued to the first character. The four-byte tests therefore run first, and
`bom_charset` returns a single row with no scoring at all.

Decoding is strict where it is cheap to be strict: a unit above U+10FFFF, a
surrogate code point (`D800..DFFF`), or a trailing fragment shorter than four
bytes each count as an error and become one U+FFFD. The leading BOM is stripped
rather than carried into the text.

### The binary rule

`looks_binary` answers a different question from `detect`: not *which encoding*
but *is this text at all*. It scans the first 8 KiB for a NUL byte and returns
true if it finds one — unless the file is UTF-16 or UTF-32 shaped, or carries a
BOM, in which case NULs are expected.

This exists because of `scan`. A directory walk that force-decodes a PNG
produces a confident-looking answer for a file that is not text, and one such
row poisons a report. The threshold is deliberately crude: real text in any
supported code page contains no NUL, and false positives only matter if a
UTF-16/32 file slips past the two evidence checks above.

## Repair

`repair(text)` runs at most four rounds. Each round tries every
`(wrong, right)` pair from:

- `wrong` ∈ {windows-1252, latin1, gbk, big5, shift_jis, euc-kr} — the code
  pages that actually get applied by mistake.
- `right` ∈ {utf-8, gbk, big5, shift_jis, euc-kr, windows-1252, latin1} — every
  code page a file could really be in.

A candidate is accepted only when it decodes with **zero errors** and improves
the score by more than 4 points. The zero-error requirement is what keeps the
search honest: a mojibake reversal that leaves malformed bytes behind is not a
reversal. The 4-point margin stops the search from "repairing" text that was
already fine into something marginally more frequent.

UTF-16 is absent from both lists. Nobody re-encodes a file to UTF-16 by
accident, and allowing it as a target made the search turn Chinese into Hangul,
which decodes cleanly and scores well. That was a real bug, and the fix was to
remove the option rather than to tune around it.

### The script guard

Removing UTF-16 as a target was necessary but not sufficient. The search is
greedy and runs four rounds, so a *second* round could still take correct
Chinese text, re-encode it as EUC-KR, decode it back, and land in Hangul — which
decodes with zero errors and scores well precisely because Hangul has no
frequency model holding it back. The JSON test for `repair` caught this: 你好
came back as 콱봤.

So each round now computes the dominant script of its input and refuses a step
that leaves Han for Hangul or kana (and vice versa, in every direction). Latin
and script-less input may go anywhere — that is the case repair exists for.

```
from Han / Hangul / kana  ->  only the same script
from Latin or script-less ->  anything
```

This is a hard veto, not a score penalty, because a 4-point margin cannot
outweigh a 90-point score. Encoding errors move text between *byte* domains;
they do not translate a language. A step that changes the language is a wrong
answer by construction.

Chains are reported, not just results: `render_chain` gives
`windows-1252 -> utf-8`, and `steps()` gives the individual pairs. A caller can
audit the reasoning instead of trusting the output.

## Known limits

- Mojibake that passed through a code page with undefined bytes is partially
  destroyed: those bytes became U+FFFD somewhere upstream and cannot be
  recovered.
- Short Western text is ambiguous by construction. Latin-1 and windows-1252 are
  byte-identical outside `0x80..0x9F`; no detector can separate them, so the
  confidence says so.
- Korean byte ranges are a subset of GBK, so Korean text decodes cleanly as
  Chinese too. Script exclusivity breaks that tie, but a short Korean string
  with no Hangul-dominant majority would still be misread.
- The frequency model covers Han characters only. Kana and Hangul get a fixed
  score because there is no frequency data behind them, which makes Japanese and
  Korean detection weaker than Chinese detection.
- Kana-only text has no tie-breaker left. A katakana string in EUC-JP decodes to
  byte-identical katakana in GBK, so both readings score the same. Since 0.5.0
  that is reported as a tie (`ambiguous`, with `gbk` and `euc-jp` listed) rather
  than as a confident `gbk`. Every mixed Japanese sample with at least one kanji
  resolves correctly.
- A GB18030 file that never leaves GBK's range is reported as GBK. Both labels
  decode it to the same text, so nothing is lost, but the label is the narrower
  one. `--from gb18030` reads such a file regardless.
